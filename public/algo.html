算法与技术

把行程排成一道
可以验证的最优化题。

行程规划不是「把高分景点按顺序念一遍」。它要在一堆互相冲突的约束里做取舍：开放时间只有几个小时、排队会临时变长、老人走不了山路、下午四点要下雨。旅迹把这件事形式化成带时间窗的团队定向越野问题（TOPTW），先贪心拿到可行解，再用迭代局部搜索把顺序改到接近最优，最后用全排列穷举反过来验证启发式有没有排错。

01

问题怎么落到数学模型上

TTDP → TOPTW

旅游行程设计问题（Tourist Trip Design Problem）在学术上是定向越野问题（Orienteering Problem）的变体：候选点各有「价值」，走一趟只能选一部分，要在时间预算内让总价值最大。加上景点开放时间窗与排队之后，它就是 TOPTW（Team Orienteering Problem with Time Windows）——已被证明是 NP-hard，规模一大就不存在多项式时间的精确解法。

符号含义在系统里的来源

si第 i 点被选中可得的价值九维加权打分（见 §03）

s.t.   Σj xij = yi  ,  Σj xji = yi   // 进了就要出，不许多停

硬约束（闭馆日、轮椅不可达、步行强度超阈值）在建模阶段就直接把变量从 V 里删掉，不进入优化——否则惩罚项会把真正的可行解一起淹掉。
02

双阶段求解：先把解做出来，再把解做对

Greedy Construction + ILS

单靠贪心只能「一直加」，加到某个点排不进就停手，永远不会回头把前面某个点换掉。所以拆成两层：内层负责在给定访问顺序下把时刻表排出来并算真实目标值，外层负责在顺序的排列空间里搜索。

内层：解析时刻表，O(n·|V|) 外层：邻域搜索，O(iters·n) 数据与约束入口
第一层 · 贪心构造 build_group

从住宿出发，每一轮在「当前还进得去」的候选里挑分最高的一个，卡死四个时刻：到达、开始游览（等开门之后）、排队结束、离开。任何一步顶到闭馆时间就整站作废。11:30–13:30 强制插午餐，低步行人群每 2.5 小时强制休息。

输出：一条可行时间轴 + 真实目标值
复杂度：O(n · |V|)，n 为当天停留点数
第二层 · 迭代局部搜索 solve_group

在「访问顺序」这个排列上做邻域扰动：交换两站、把一站挪到别的位置、把一个没排上的点插进来。每一次扰动都交给第一层按新顺序重排时刻表，只接受目标值严格变好的解；连续 stall ≥ 4 轮没有改进，就把一次扰动加到两次、三次。

输出：改进后的顺序 + 收敛轨迹
默认 160 轮，实测 15–20 ms
这是本次迭代里最关键的一次改动。最初两层的职责被搞反了——外层只是调九维分数的权重，内层贪心照着新权重重排。结果无论怎么调权重，gap 都卡在 12.35% 下不去，因为权重只能改变「哪个点分高」，改不动「先去哪」这种顺序性决策。把搜索空间从「权重向量」换成「访问顺序的排列」之后，真实算例的 gap 从 12.35% 直接降到 0。
03

九维评价：定量、半定量、定性各管一段

4 定量 + 2 半定量 + 3 定性

单一评分会把完全不同的信息压成一个数，评审看不出为什么。所以拆成九个维度，每一项标明数据来源的性质：定量项直接来自数据字段，半定量项由规则映射到区间，定性项由标签体系判断。界面上把这张表原样摊开，每个停留点每一维的得分都能逐格看到。

维度类型权重取值方式作用方向
rating定量2.0点评分 × 2口碑越好分越高
interest定性9.0命中一个用户兴趣标签 +9权重最高，决定主线
crowd定性4.0亲子 / 情侣标签匹配 +3~4；周末户外 −1人群适配
weather半定量4.0降水概率 ≥60% 时室内 +4 / 户外 −4；晴天户外 +2天气折价
access定性4.0轮椅需求且景点可达 +4无障碍准入
walk半定量2.2−(步行强度−1) × 2.2（低步行人群）/ × 0.6（常规）体力成本
queue定量1/12−min(基础排队, 40) / 12排队成本
travel定量1/12−转场分钟 / 12路上成本
ticket定量1/120−票价 / 120门票成本

权重不是拍脑袋：时间成本（排队、转场）按「1 分钟值多少分」统一到同一量纲，门票按「10 元 ≈ 0.08 分」折算，兴趣与人群这类决定「这趟值不值得来」的因素权重必须显著高于交通噪声，否则排序会被排队时长主导。

04

邻域算子和接受准则

三种扰动 + 严格改进
交换 op < 0.45

随机取两个已排入的位置互换。用来看「A 和 B 谁该在前」——最便宜也最常用的修正。

swap(i, j)
移动 op < 0.85

把一站从原位置抽出，插到任意其它位置。能修掉「顺序整体偏了」这类交换解决不了的结构问题。

insert(j, pop(i))
引入新点 else

从「本来是落选」的候选池里随机挑一个塞进序列。贪心一旦漏掉某个点，只有这一步能把它捞回来。

insert(rand, choice(spare))
  • 构造初始解：贪心按九维得分排出第一版时间轴，得到初始目标值 base。
  • 扰动：按概率抽算子，连续扰动 1 + stall//4 次（上限 4 次）——停滞越久，破坏力度越大。
  • 重排与评估：把新顺序交给内层按同样的时间窗、排队、午餐规则重排时刻表，算真实目标值。
  • 严格接受：只有目标值严格大于历史最优才替换 best，不做「以一定概率接受变差解」的退火——目标值口径必须和验证阶段完全一致，否则 gap 就没意义。
  • 记录轨迹：每一轮的最优值入栈，前端画成阶梯曲线。曲线只升不降，跳升点就是找到更好顺序的时刻。
05

最优性验证：用穷举反过来考自己

Exhaustive Enumeration as Ground Truth

启发式最大的风险是「看起来排得挺顺，其实漏了更好的解」。所以单独写了一个没有任何启发式干预的评估函数 eval_order：给定一个访问顺序，直接按真实规则推时刻表、算真实得分，不剪枝、不折价、不猜。然后用它穷举 n 个景点的全部 n! 种顺序，得到可证明的最优值，再和 ILS 的结果对比。

黑盒算法没人敢用

一个排得再好的行程，如果用户不知道为什么这么排、为什么没排那个，就不会采纳。所以求解过程被完整暴露到界面上：

落选归因

没进行程的点分三类：硬约束出局（闭馆 / 轮椅不可达 / 坡度超标）、前几天已去过、评分未进前列。每类都给出具体原因，不写「综合考量」。

收敛曲线

贪心构造值、ILS 最优值、提升幅度、改进轮次、每一轮的轨迹，全部来自真实运行，不是示意。

07

已知局限与下一步

诚实比漂亮重要
  • 单目标加权，不是帕累托前沿：九维被压成一个标量，权重变化会改变解的取舍。下一步可以做多目标（时间 / 花费 / 兴趣）的帕累托集，让用户自己挑。
  • 排队模型是经验系数：午高峰 ×1.6、周末 ×1.25、雨天室内 ×1.3 都来自规则而非真实客流。接入真实预约接口后，这一项应该换成数据驱动的。
  • 天气只有一个样例源：本地 4 天样例，多日行程超出范围的部分按气候外推，界面上明确标注了「外推」。
  • 多日是逐日求解，不是全局联合优化：把 N 天拆成 N 个耦合子问题，跨天只共享「已去过」集合。真正的联合优化要把 N 天放进同一个时间轴，规模会比现在大一个量级。
  • 穷举验证只在小规模成立：n 超过 10 之后全排列不可行，需要换用整数规划求解器（如 OR-Tools 的 CP-SAT）作为下界参考。
