# 旅迹 LVJI · 一日行程编排（挑战 2）

一句话 → 一天可执行的行程：多站点排序、开放时间与排队、天气 / 交通 / 住宿、单人 / 分组、无障碍标注。
**自建前端 + 本地数据 + 本地 mock API**，不依赖任何外部接口。

## 启动

```bash
python3 main.py            # 默认 0.0.0.0:8000，可用 PORT / HOST 覆盖
python3 -m unittest tests.test_planner
```

打开 `http://localhost:8000/`，页面会自动跑一次示例。

## 数据接口（本地 mock API）

| 接口 | 返回 | 用途 |
|---|---|---|
| `GET /api/meta` | 数据集概览、版本、今日 | 首屏数据规模 |
| `GET /api/spots` | 14 个景点的开放/闭馆时间、闭馆日、排队分钟、步行强度、室内外、票价、无障碍标签、经纬度 | 排程主数据 |
| `GET /api/weather` | 4 天样例（天气、气温、降水概率、户外适宜度） | 天气纳入排程 |
| `GET /api/transport` | 6 条城际车次/航班 + 市内步行/地铁/打车参数 | 交通与预算 |
| `GET /api/hotels` | 4 家住宿样例（价格、星级、无障碍、停车） | 住宿与预算 |
| `GET /api/benchmark` | 真实景点算例：全排列穷举最优 vs ILS，含 gap | 最优性验证 |
| `GET /api/scaling` | n=4..8 的规模曲线：排列数、穷举耗时、ILS 耗时、gap | 算法规模证据 |
| `POST /api/plan` | 一句话 → 完整行程 JSON（含 `apiCalls` 调用记录） | 核心编排 |

`POST /api/plan` 返回的 `apiCalls` 是「数据真实性」的验证依据：每次调用的接口名、耗时、返回行数都在响应里，前端原样展示。

## 数据里有什么（`data/*.json`）

- **景点**：`open` / `close` / `closedDays`（周一闭馆）、`queueMin`（分时段×1.6，周末×1.25，雨天室内×1.3）、`durationMin`、`walkIntensity` 1–5、`indoor`、`ticket`、`wheelchair` / `accessibleToilet` / `aed` / `parking`、`zone`、`lat` / `lon`
- **天气**：`rainProb`、`outdoorScore`、`tip`
- **交通**：城际 `code` / `depart` / `arrive` / `price`；市内 `步行 4.5km/h`、`地铁 22km/h + 候车 6min`、`打车 26km/h + 等车 5min`
- **住宿**：价格、星级、无障碍与停车位

## 排程算法

形式上这是一个**带时间窗的团队定向问题（TOPTW, Team Orienteering Problem with Time Windows）**——旅游行程设计问题（TTDP）的学术核心：在开放时间窗与当天时间预算下，选出并排序一批景点，使总价值最大。它是 NP-hard 的，不能靠枚举。

实现分两层：

### 第一层：贪心构造（经典）

1. **理解**：正则提取城市、人数（含「带爸妈 / 两个孩子」这类推算）、同行人群、兴趣、时段、轮椅与低步行约束、日期（对齐天气样例）
2. **过滤**：闭馆日、轮椅不可达、步行强度超阈值直接排除
3. **打分**：九维加权，见下表
4. **排时**：每轮取当前可进入点里分最高的插入，卡死「到达 → 排队 → 游览 → 闭馆」四个时刻；11:30–13:30 强制留午餐（窗口 < 5.5 小时则不排正餐）
5. **分组**：同时有长辈和孩子时拆两组各自排程；亲子组继承长辈组的午餐店作为汇合点，并避开长辈组已选景点错峰
6. **记账**：门票 × 人数 + 市内交通 + 餐费 + 住宿 + 城际

### 第二层：ILS 顺序空间邻域搜索（改进）

纯贪心是单向的：一旦决定了「先去哪」，后面全部连锁。为了改变「先去哪」这种**结构性决策**，外层在**访问顺序这个排列空间**上做迭代局部搜索（ILS）：

- **邻域算子**：交换两站 / 把一站挪到另一个位置 / 把此前没排上的候选点插进来
- **评估**：按给定顺序重新排整张时刻表，算真实目标值
- **接受准则**：只接受更优解；连续无改进则加大扰动力度（最多 4 次复合移动）
- **固定随机种子**：结果可复现，演示不会因随机性抖动

实际效果（「带坐轮椅的奶奶 + 两个孩子」这一需求）：构造 91.9 分 → 搜索后 98.1 分，**+6.8%**，多排出 1 个景点。

### 九维评价指标

| 维度 | 性质 | 权重 | 说明 |
|---|---|---|---|
| 口碑 | 定量 | ×2 | 评分 × 2 |
| 兴趣匹配 | 定性 | 9 | 命中一个兴趣 +9 |
| 人群适配 | 定性 | 4 | 亲子/情侣标签加分 |
| 天气适配 | 半定量 | 4 | 降水概率与室内外 +4/−4 |
| 无障碍 | 定性 | 4 | 轮椅可达 +4 |
| 步行强度 | 半定量 | 2.2 | 强度越高扣分越多 |
| 排队成本 | 定量 | 1/12 | 排队分钟 / 12 |
| 路上耗时 | 定量 | 1/12 | 移动分钟 / 12 |
| 门票成本 | 定量 | 1/120 | 票价 / 120 |

### 最优性验证

`GET /api/benchmark` 与 `GET /api/scaling` 会把 ILS 的结果与**全排列穷举的可证明最优**做对比：

| 规模 | 排列数 | 全穷举 | ILS | gap | 加速 |
|---|---|---|---|---|---|
| n=4 | 24 | 0.4 ms | 8.9 ms | 0% | 0× |
| n=5 | 120 | 2.7 ms | 10.9 ms | 0% | 0.2× |
| n=6 | 720 | 18.1 ms | 12.9 ms | 0.08% | 1.4× |
| n=7 | 5,040 | 147.4 ms | 14.8 ms | 0.37% | 10× |
| n=8 | 40,320 | 1,391.8 ms | 18.5 ms | 0.06% | 75× |

真实景点算例上 3/3 组都命中了穷举最优（gap 0%）。规模从 4 到 8，穷举耗时涨约 3500 倍，ILS 只涨 2 倍——这就是启发式的价值边界。

## 对应赛题要求

| 要求 | 落点 |
|---|---|
| 1 模糊输入理解 | `parse_request()`：一句话取城市/人数/人群/兴趣/时段/无障碍，输出含时间、地点、顺序、理由 |
| 2 多站点路线 | 贪心构造 + ILS 顺序搜索；前端 SVG 等比投影路线图 + 到访序号与时刻清单 |
| 3 时间窗与排队 | 每站 `begin = max(到达, 开门)`，`队列 × 时段/周末/天气系数`，`leaving ≤ closeTime` |
| 4 天气 / 交通 / 住宿 | 天气影响选点与提示；市内三档交通算耗时与费用；城际与住宿进预算 |
| 5 单人与多人 | 一人一队；长辈+孩子自动拆组、各排各的、午餐汇合、撞点错峰 |
| 6 特殊人群 | 轮椅可达 / 无障碍厕所 / AED / 停车位逐点在时间轴与「无障碍与配套」卡片中标出 |
| 7 前端体验 | 时间轴、路线图、预算卡、接口日志、分组 tab、chips、响应式与 reduced-motion |
